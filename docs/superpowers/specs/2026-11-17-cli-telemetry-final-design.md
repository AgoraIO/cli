# CLI 使用埋点最终方案

日期：2026-11-17

状态：用户已确认功能范围；2026-11-17 已按本方案完成 CLI 与 SSP 本地实现及本机验收。Linux/Windows 实际运行与真实 PostHog UUID/入库验证仍待完成，未启用生产采集。详见 [本地验收记录](../plans/2026-11-17-cli-telemetry-verification.md)。本文取代此前方案中与本文冲突的埋点设计。

## 目标与范围

了解开发者如何使用 Recipes、初始化 Demo 和创建项目，以及这些操作的结果。采用默认采集、首次告知、允许退出的方式；事件产生后通过管道交给独立子进程逐条发送，业务命令不等待埋点网络请求。

埋点仍是新功能，直接修改开发中的实现，不保留显式同意机制或中间版本协议的兼容逻辑。此前已有的关闭设置继续有效。

## 1. 开启、告知与关闭

默认开启，但只有采集地址已配置且本地偏好有效时才实际采集；当前源码内嵌地址为空，修改默认策略本身不会接通生产采集。第一次符合采集条件的被采集命令运行前，向 stderr 展示采集范围、说明链接和关闭方法，不询问、不要求用户确认。展示成功后，在私有配置目录保存一个告知标记，以后不重复提醒。

本地设置的职责如下：

| 设置 | 含义 |
| --- | --- |
| `telemetryEnabled` | 用户保存的采集开关，默认开启 |
| 独立告知标记文件 `telemetry-notice-shown` | 文件存在表示展示过说明，不代表明确同意；不通过重写 config.json 保存这个标记 |

告知标记与开关配置分开，避免仅为保存“展示过”而覆盖另一条命令刚写入的关闭设置。不为告知建设锁或多版本机制；并发首次运行可能重复提醒，标记写入失败可能下次再次提醒，这些情况都不能阻止业务命令。此处是首次提醒的尽力记录，不保证并发情况下严格只展示一次。

删除 `telemetryConsent`、首次运行的 `[y/N]` 询问，以及相关采集判断、返回字段、文档和测试。不增加 consent 迁移逻辑。

普通终端、JSON、CI、Agent 和 MCP 使用相同的采集策略。说明只写 stderr，不能污染 JSON 或 MCP 的 stdout。MCP 在服务启动时按上述条件展示说明；quiet 模式不展示，也不标记为已展示，后续非 quiet 运行再提醒。help、version、shell completion、内部发送入口不触发告知或采集；telemetry disable 不触发开启说明。telemetry enable 在写入开启设置后按相同规则告知，是否生效仍由地址和退出设置决定。写出告知失败不能让业务命令失败。

用户可以随时关闭：

```bash
agora telemetry disable
DO_NOT_TRACK=1
AGORA_TELEMETRY_ENABLED=0
```

保留 `agora telemetry enable` 重新开启。环境变量退出优先于保存的开关，enable 不能覆盖它。关闭设置从下一次命令或工具调用生效，此后不生成事件、不启动发送子进程；已经开始的操作可能仍会发送。升级不会重新开启。

`telemetry status` 移除 consent 相关内容；enabled 明确表示保存的偏好，captureActive 表示结合运行时退出设置和地址后的实际状态，transportConfigured 只表示本地有合法地址，不表示远端已启用或数据已入库。修正当前 enabled 混入 DO_NOT_TRACK 的实现与说明，不引入新状态体系。沿用现有运行时退出语义，包括任何非空 DO_NOT_TRACK、AGORA_TELEMETRY_ENABLED=0，以及当前代码仍支持的显式 AGORA_SENTRY_ENABLED=0；不扩展异常报告链路。

普通 CLI 使用启动时加载的埋点开关；MCP 每次工具调用开始时读取一次本地 config.json 中的埋点开关，本次操作沿用该结果。交接事件和子进程发送时不再读取配置。MCP 读取埋点开关失败时，放弃本次采集，不影响工具调用；CLI 原有的配置加载及错误处理保持不变。

## 2. 记录哪些行为

覆盖下列命令及对应 MCP 工具：

| 操作 | 事件 | 记录内容 |
| --- | --- | --- |
| 查看 Recipes 列表 | `cli_recipes_list_completed` | 结果、耗时、成功时的结果数量 |
| 查看 Recipe 详情 | `cli_recipes_show_completed` | 结果、耗时、公开 Recipe 标识 |
| 初始化 Demo | `cli_init_started`、`cli_init_stage_completed`、`cli_init_completed` | 开始、各阶段结果、最终结果、耗时和失败阶段 |
| 创建项目 | `cli_project_create_completed` | 创建结果、耗时、成功后取得的 Agora App ID |

沿用已有的阶段定义、结果、稳定错误码、退出码、公开 Recipe/模板标识、CLI 版本、操作系统、架构、AI 工具类别及调用渠道。不扩大到所有 CLI 命令。

### 项目创建的处理

- 直接执行 project create：记录一次项目创建结果。
- init 内部创建项目：也记录一次项目创建结果，与本次 init 共用单次执行标识。
- init 复用项目：不产生创建事件，继续记录复用结果。
- 本地校验失败、dry-run、help：未调用 createProject，不产生项目创建事件。
- createProject 返回错误：记录本次调用失败，未取得 App ID 就省略；这不能证明创建请求已发出，也不能证明服务器没有创建项目。
- 创建成功、后续初始化失败：创建事件记成功，init 事件记失败。

使用现有 `command` 区分顶层入口 project create 和 init，沿用 `invocation_channel` 区分 shell 和 MCP，不再新增含义重复的 source_command。

项目创建事件在共享的 createProject 调用边界记录，调用方传入本次 operation；每次调用记录一次结果，不能在 shell 包装层、MCP 包装层和 init 内重复记录。从调用开始到返回结果计时，包含内部登录、Token 刷新及重发，不包含后续功能启用、配置写入和克隆。沿用 createProject 的返回结果判断成功或失败，不为埋点跟踪每次 HTTP 请求是否实际发出，也不增加业务响应校验。调用成功后立即在内存中记录成功并保存合法 App ID，缺失或格式不合法时省略，再执行启用功能、写上下文和后续查询。两种 init 来源（Recipe 与 Quickstart）、shell 与 MCP 都必须覆盖。

事件 success 表示 createProject 调用返回成功；failure 表示该调用返回错误，可能发生在认证、请求或响应处理阶段，既不是数据库事务断言，也不代表项目创建全流程的最终状态。服务端可能已经写入项目，但后续处理或响应传输失败。本次不为消除这种不确定性新增业务查询或事件。

统计时使用“创建调用返回成功的次数”，不称为完整的真实创建数量。不把 init 中的 created 标记再计一次；需要查看观测到的不同项目数量时，对带有 app_id 的成功事件按 app_id 去重。网络丢失、进程终止和重复调用都可能影响统计，埋点不承担项目台账职责。

这里的创建结果指项目资源创建本身，不能因为后续启用功能、写配置或克隆失败，就把已经创建成功的项目记为创建失败。

## 3. 如何关联数据

| 标识 | 用途 |
| --- | --- |
| 随机安装标识，即现有 `distinct_id` | 保存在本机配置目录，跨命令复用；关联同一安装的历次使用，不代表已验证的自然人 |
| 现有 `operation_id` | 每次命令或 MCP 工具调用生成；把同一次执行中的多条事件串起来，重试生成新值 |
| `app_id` | Agora 项目的 App ID；关联同一项目的操作 |
| 现有 `event_id` | 仅用于 CLI 到 SSP 链路内部去重，不作为 PostHog UUID 或事件属性转发 |

安装标识沿用当前随机生成和私有文件存储方式。删除该文件后重新生成，不代表删除已经采集的数据。

App ID 从本次操作实际创建或解析出的项目取得；仅接受符合项目 App ID 格式的值，不接受自由文本。项目创建请求成功后立即保存，不能等到 projectCreate 整个包装流程返回，因为后续启用功能或查询可能失败。

每次 operation 最多关联一个实际目标 App ID。每条事件生成时，已确认 App ID 才附加，尚未确认时省略；不回填或重新发送早期事件。同次操作的开始、阶段、创建和最终事件通过 operation_id 关联。项目创建成功事件以及之后的 init 事件可携带当时已经确认的 App ID；复用项目时，在解析出目标项目后附加。不读取全局项目来猜测；Recipes 查询不附加项目。

这里的 `app_id` 对应项目响应中的 `appId`，不是 SSP 认证上下文里的 OAuth 客户端 `appid`。

不获取用户 ID、公司 ID，不新增身份查询或身份缓存，不修改业务 API 的返回。不添加 region、project_id 或 session_id，不做网站用户画像合并。

### PostHog UUID

SSP 转发事件时省略顶层 `uuid`，由 PostHog 自行生成。删除当前 `uuid: event.event_id` 的映射，也不再把内部 event_id 作为普通属性转发。

SSP 内部的去重编号与 PostHog 的事件编号各自独立。PostHog 自动生成 UUID 只是在接收时编号，不等于能识别两次 HTTP 投递是否属于同一条事件。SSP 沿用现有去重机制及其边界：去重表仅在单个进程内有效，跨副本或重启后的重复可能再次进入 PostHog；不宣称端到端恰好一次，不增加跨实例去重基础设施。

待验证：PostHog 省略 uuid 后自动生成的行为。本文尚未附可复查的源码依据，也未验证实际使用的部署版本。启用前需验证该部署确实接受省略 uuid 的事件，且查询结果具有自动生成的 UUID；验证失败时报告阻塞，不悄悄恢复自定义 UUID。

## 4. 何时交接与发送

事件产生后即交给后台发送，不等命令结束汇总。第一次产生事件时启动一个发送子进程，同次操作的后续事件复用它，不为每条事件启动新进程。

```text
主命令：产生事件 → 交给后台管道写入任务 → 继续业务
发送子进程：从管道读取事件 → 逐条 POST 到 SSP → SSP 转发给 PostHog
命令结束：记录最终事件 → 结束本地交接并关闭管道 → 返回
发送子进程：收到 EOF → 在有限时间内发送剩余事件 → 退出
```

Recipes、project create 的结果事件产生后发送。init 的开始、各阶段、内部项目创建和最终结果分别在产生时交接，不等 init 结束。MCP 每次被采集的工具调用使用自己的发送子进程，调用结束时关闭该管道，不等待整个 MCP 服务退出。

同一个二进制通过 os.Executable 定位自身，直接启动隐藏内部发送入口，不通过 shell，也不依赖 PATH 上的 agora。事件通过子进程 stdin 管道传入，每行一个 JSON 事件（NDJSON），不放入命令行参数。内部入口在常规 App 初始化前识别，只负责发送，不运行业务命令、不打印首次告知、不递归埋点。

主进程根据本次操作开始时确定的采集状态决定是否启动发送子进程，并传入合法采集地址；采集地址不进入事件。子进程不重新读取配置或埋点开关，不读取 session 或刷新登录。内部发送入口通过专用分支避免递归。

### 不影响业务命令

业务代码只向有界内存缓冲提交事件，由后台写入任务写管道。子进程的管道读取与 HTTP 发送分开，避免网络变慢直接堵住管道。父子进程各自的待发送事件缓冲最多 20 条；缓冲满时丢弃新事件，不阻塞业务，不引入持久队列或调度系统。

命令结束时提交最终事件，完成有界的本地交接并关闭管道；管道阻塞或断开时放弃尚未交接的事件，不能无限等待管道写入。业务命令不等待 DNS、TLS、HTTP 响应或 PostHog 入库。启动和本地交接仍有开销，不承诺绝对零延迟。

子进程通过 stdin 接收事件，stdout 和 stderr 接空设备，避免保留调用方输出管道。子进程脱离父进程，使用独立 HTTP 客户端，不携带业务认证，拒绝重定向与请求重放；每条事件单独发一个 HTTP 请求，沿用 SSP 的请求结构 {"events":[event]}，不修改接收接口为新协议。发送失败或超时丢弃该事件，不重试、不补发。

每次 HTTP 请求最多三秒。子进程在命令运行期间持续接收事件，不从启动起设置三秒总 deadline；收到管道 EOF 后，最多再用三秒处理剩余事件，然后退出，未发送完的允许丢失。网络请求和收尾超时独立于父命令的取消 context，父进程不等待子进程发送完成。发送结果不改变业务输出和退出码，普通 debug 不切换为阻塞发送。

这些超时是运行中的任务预算，不是操作系统对进程存活时间的硬保证，无法覆盖系统挂起。正常父进程退出后子进程应可继续处理已收到的事件，但 CI 容器退出、进程组清理、Windows Job Object 等外部机制仍可能一并终止它，此时允许丢失事件。

父进程存活时异步等待并回收发送子进程，不用 Wait 阻塞主命令。每个父进程最多两个发送子进程同时在途；某次操作首次产生事件时若已满额，就放弃该次操作的采集，不在后续阶段反复尝试启动。这个上限用于约束 MCP 长进程的资源占用，不提供跨独立 CLI 进程的全局限制。macOS、Linux、Windows 分别验证进程脱离和回收。

### 数据丢失与大小限制

沿用 SSP 每事件 4 KiB 的限制，超限只丢弃该事件，不截断 JSON，不连带丢弃同次操作的其他合法事件。CLI 每次请求只有一条事件，SSP 接口原有的每批最多 20 条、每请求最多 64 KiB 的限制保持不变。不增加 CLI 的 16 KiB 批次限制，也不再通过命令行参数传递事件。

崩溃、强制终止、缓冲满、管道交接失败、进程启动失败、超时或服务拒绝都可能丢失事件。已发送的开始或阶段事件可能没有对应最终事件；缺失最终事件不能直接解释为业务失败。方案不承诺必达，也不引入磁盘队列、临时事件文件、常驻服务或下次运行补发。

管道中只允许经过白名单筛选的事件，不得包含 Token 等秘密。

## 5. SSP 与 PostHog 的改动

继续使用现有链路：CLI → SSP collector → PostHog。

SSP 只修改埋点接收协议、对应校验与转发：增加项目创建事件、app_id，以及 command=project create，移除对 PostHog UUID 的赋值及 event_id 属性转发。事件字段和 App ID 必须受白名单、格式及长度限制，不能只在 CLI 端约束。

必须同步修改 collector 的事件与命令匹配规则：init 允许现有 init 事件及嵌套的 cli_project_create_completed；project create 允许项目创建事件；recipes 保持各自事件匹配。当前代码对 init 只接受 cli_init_ 前缀，若只更新 schema，新增创建事件会被拒绝。项目创建事件的 outcome、duration_ms、exit_code 是 createProject 调用自己的结果，不能套用外层 init 的最终退出码。

保留现有大小限制、限流、内部事件去重和环境标记；保留关闭 person profile 处理及 GeoIP 的设置。采集地址为空、SSP 未配置转发 Token、远端返回错误都不构成 CLI 业务失败；status 的本地配置状态不证明远端可用。

不新增业务接口，不修改业务接口返回，不增加身份关联、协议版本或开发中间版本的兼容机制。

不采集代码、对话、密钥、完整命令、本地路径、项目名称或原始错误正文，不向 PostHog 转发认证信息或客户端 IP。异常报告属于另一条链路，不在本方案范围内。

## 6. 验收标准

- 默认采集、首次告知、关闭和重新开启符合上述规则；无采集地址时不发送；help、dry-run、disable 的行为正确，告知或标记写入失败不影响业务，告知记录不改写关闭偏好。
- JSON 和 MCP stdout、业务输出及退出码不变。
- 直接创建和 init 内部创建各记录一次；复用项目不计为创建。
- 创建调用的耗时包含内部认证及重发，排除后续功能启用、配置写入和克隆；认证失败也只记录本次调用的一条失败事件。
- 项目创建响应成功、后续功能启用失败或查询失败能够分别反映，App ID 不因外层返回失败而丢失；Recipe 与 Quickstart 的 shell/MCP 路径、复用路径均覆盖。
- 创建调用超时只能解释为调用未正常完成，不能声称服务器没有创建；统计说明区分调用返回成功次数与按 App ID 去重的观测项目数量。
- 早期事件不回填后来确认的 App ID，通过 operation_id 与后续事件关联；已确认 App ID 后产生的相关事件携带它。嵌套创建事件和 init 事件的结果、耗时与退出码各自正确，SSP 逐条接收通过。
- SSP 转发不携带顶层 uuid 或 event_id 属性，内部去重仍有效。
- init 尚未结束时，本地接收器就能收到开始及已完成阶段事件；每次 HTTP 请求只含一条事件，同次操作最多启动一个发送子进程。
- 正常主进程退出后子进程仍能处理已收到的事件；单次 HTTP 请求最多三秒，EOF 后收尾最多三秒。持续超过三秒的业务操作不会使发送子进程提前退出；异常宿主清理导致丢失不伪装成发送成功。
- 超限、MCP 读取埋点开关失败、发送子进程启动失败不影响业务结果；CLI 原有的配置错误处理保持不变。
- 合法最长字段的单事件不超过 4 KiB；NDJSON 管道能正确区分完整事件，多阶段 init 不受总事件数据大小限制。单事件超限不影响其他合法事件发送。
- 三个平台的进程脱离、管道关闭、输出句柄和资源回收经过验证；接收端变慢或不读取管道时，缓冲和本地交接仍有界，不阻塞业务。MCP 最多两个在途子进程，满额时放弃新操作的采集，不阻塞工具返回。
- 普通 CLI 沿用启动时的埋点开关，MCP 每次工具调用开始时读取一次；交接和子进程发送时不再读取。自定义 AGORA_HOME 下也遵守关闭设置从下一次命令或工具调用生效的规则，已开始的操作允许继续发送。
